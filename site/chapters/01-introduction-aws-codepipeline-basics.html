কেন CI/CD দরকার — আসল কারণ

সহজ কথায়: তুমি code লিখলে, সেটা production-এ যেতে হলে কতগুলো ম্যানুয়াল কাজ করতে হয় — build করো, test করো, zip বানাও, server-এ copy করো, restart করো। এই একই কাজ বারবার মানুষ করলে ভুল হবে, দেরি হবে।

CI/CD এই পুরো process-টাকে code push করলেই automatically চালায়।

Continuous Integration (CI)Continuous DeliveryContinuous Deployment
কী করে Code push → build + unit test CI + staging deploy + manual approval → production CI + staging deploy + automatic production deploy
Human needed? না হ্যাঁ (approve করতে) না
AWS CodePipeline-এ? ✅ ✅ (Manual approval action) ✅

AWS CodePipeline হলো এই পুরো workflow-এর orchestrator — সে বলে কখন কী চলবে। নিজে build বা deploy করে না; সেটা CodeBuild বা CodeDeploy করে।

Pipeline-এর মূল Building Blocks

একবার মাথায় ঢুকলে বাকি সব সহজ হয়ে যাবে:

flowchart LR P["🗂️ Pipeline\n(workflow)"] S1["📦 Stage\n(Source)"] S2["🔨 Stage\n(Build)"] S3["🚀 Stage\n(Deploy)"] A1["Action\nS3 Source"] A2["Action\nCodeBuild"] A3a["Action\nDeploy EU"] A3b["Action\nDeploy US\n(parallel)"] ART["S3 Artifact\nStore"] P --> S1 --> S2 --> S3 S1 --- A1 S2 --- A2 S3 --- A3a S3 --- A3b A1 -->|SourceArtifact| ART ART -->|BuildArtifact| A3a ART -->|BuildArtifact| A3b

Pipeline-এর hierarchy: Pipeline → Stage → Action Group → Action। Artifact store দিয়ে data pass হয়।

Pipeline
পুরো workflow-এর নাম। একটি pipeline-এর নাম পরে পরিবর্তন করা যায় না।
Stage
Logical grouping। যেমন: Source, Build, Staging, Deploy। একটি stage একসাথে একটিমাত্র execution process করতে পারে — সে সময় stage "locked" থাকে।
Action
একটি stage-এর ভেতরে real কাজ। যেমন: "S3 থেকে source নামিয়ে আনো" বা "CodeBuild দিয়ে build করো"।
Action Group
একই stage-এর ভেতরে action-এর execution order নির্ধারণ করে। একই group-এ থাকা action-গুলো parallel-এ চলে।
Transition
দুই stage-এর মধ্যে "gate"। Enable বা disable করা যায়। Disable থাকলে execution সেখানে আটকে থাকে।
Artifact
একটি action-এর output file যা পরের action-এর input হয়। সব artifact S3 artifact store-এ জমা থাকে।
Source Revision
Source location-এ যে change pipeline trigger করে। প্রতিটি revision-এর unique ID থাকে (S3 version ID বা Git commit ID)।
Pipeline Execution
একটি specific source revision-কে pipeline-এর মধ্যে দিয়ে run করানো। প্রতিটি execution-এর unique execution ID থাকে।
Artifact Store: CodePipeline নিজেই একটি S3 bucket তৈরি করে এবং সব artifact সেখানে রাখে। নাম হয় codepipeline-REGION-ACCOUNT_ID। একটি region-এ সব pipeline এটি share করে।

Execution Modes — Queued, Superseded, Parallel

একই সময়ে multiple commit push করলে pipeline কীভাবে behave করবে সেটা execution mode ঠিক করে:

flowchart TD Q["QUEUED (default)\nনতুন execution আগেরটি শেষ হওয়ার\nঅপেক্ষা করে (queue)"] S["SUPERSEDED (পুরনো default)\nনতুন execution stage-এর মাঝে\nআটকে থাকা আগেরটিকে replace করে"] PA["PARALLEL\nসব execution একসাথে চলে\nকোনো queue বা replacement নেই"] Q -->|"Deploy দেরি করলে"| NOTE_Q["পুরনো আর নতুন দুটোই queue-তে থাকে"] S -->|"পুরনো stage-এর বাইরে থাকলে"| NOTE_S["পুরনোটি SUPERSEDED হয়"] PA -->|"সবসময়"| NOTE_PA["সব parallel, race condition সম্ভব"]

V2 pipeline-এর তিনটি execution mode — behavior মাথায় রাখলে অনেক production bug এড়ানো যায়।

Superseded কখন হয়? শুধুমাত্র যখন পুরনো execution দুটো stage-এর মাঝে (transition-এ) আটকে থাকে। Stage-এর ভেতরে lock নিয়ে ফেললে সেটাকে supersede করা যায় না।

প্রথম Pipeline: S3 → S3 Deploy

লক্ষ্য: একটি zip package source S3 bucket-এ upload করলেই automatically production S3 bucket-এ deploy হবে।

flowchart LR DEV["তুমি\nmy-website.zip upload করো"] SRC["Source S3 Bucket\nversioning: ON\nregion: eu-west-1"] CW["CloudWatch Events\nPutObject detect করলে trigger"] ART["S3 Artifact Store\ncodepipeline-eu-west-1-xxxx"] PROD["Production S3 Bucket\nstatic website hosting: ON\nregion: যেকোনো"] DEV -->|PutObject| SRC SRC -->|event triggers pipeline| CW CW -->|Source Stage runs| ART ART -->|Deploy Stage extracts & copies| PROD

S3 → S3 pipeline-এর end-to-end flow। Source bucket-এ zip upload হলে production bucket-এ সাইট deploy হয়।

ধাপ ১ — Source S3 Bucket তৈরি করো

  1. S3 Console → Create bucket
  2. Region: eu-west-1 (pipeline-এর region-এর সাথে same রাখো)
  3. Name: my-website-source-<unique-suffix>
  4. Scroll down → Bucket Versioning: Enable ✅
    এটা না করলে CodePipeline source হিসেবে এই bucket accept করবে না। Versioning থেকে CodePipeline বোঝে কোন version deploy করতে হবে।
  5. Create bucket

ধাপ ২ — Production S3 Bucket তৈরি ও Configure করো

  1. আবার Create bucket
  2. Name: my-website-prod-<unique-suffix>
  3. Block all public access: OFF করো → acknowledge করো (static website চালাতে হবে তাই)
  4. Create bucket → bucket details খোলো
  5. Permissions tab → Bucket policy → Edit → নিচের JSON paste করো:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
  }]
}
  1. Properties tab → Static website hosting → Edit → Enable
  2. Index document: index.html · Error document: error.html → Save

ধাপ ৩ — Source Package Upload করো

index.html আর error.html — দুটো file সরাসরি zip করো (folder zip করবা না!)। নাম দাও: my-website.zip। Source bucket-এ upload করো।

ধাপ ৪ — Pipeline তৈরি করো

  1. CodePipeline Console → Create pipeline → Build custom pipeline → Next
  2. Pipeline name: MyWebsitePipeline (নাম পরে বদলাবে না)
  3. Pipeline type: V2 (only option) · Execution mode: Queued
  4. Service role: New service role — CodePipeline নিজে তৈরি করুক
  5. Artifact store: Default location → Next
  6. Source Stage:
    • Provider: Amazon S3
    • Bucket: তোমার source bucket
    • S3 object key: my-website.zip
    • Change detection: Amazon CloudWatch Events ✅ (polling করবা না)
  7. Next → Skip build stage → Skip
  8. Deploy Stage:
    • Provider: Amazon S3
    • Region: eu-west-1
    • Bucket: production bucket
    • ✅ Extract file before deploy — না করলে zip ফাইলটাই deploy হবে, HTML file না
  9. Next → Review → Create pipeline
Pipeline তৈরির সাথে সাথে automatic একটি execution শুরু হবে। Source bucket-এ যে zip আছে সেটা deploy হবে।

তৈরি হওয়ার সাথে সাথে AWS কী কী বানায়

  • S3 Artifact Store: codepipeline-eu-west-1-ACCOUNT_ID — এই region-এর সব pipeline এটা share করে
  • CloudWatch Events rule: Source bucket-এর PutObject event catch করে pipeline trigger করে। CloudTrail-এর মাধ্যমে কাজ করে।
  • IAM roles: Pipeline service role + EventBridge trigger role

Source Change Detection কীভাবে কাজ করে

sequenceDiagram participant DEV as তুমি participant S3 as Source S3 participant CT as CloudTrail participant CW as CloudWatch Events Rule participant CP as CodePipeline DEV->>S3: PUT my-website.zip (new version) S3->>CT: PutObject API call logged CT->>CW: Event emitted CW->>CP: Trigger pipeline execution Note over CP: Source Stage শুরু হয় CP->>S3: zip download করে artifact store-এ রাখে

S3 source-এর change detection chain: তুমি upload করলে → CloudTrail log → CloudWatch event → pipeline trigger।

দুটো detection option:

  • Amazon CloudWatch Events (recommended) — near real-time। Upload হওয়ার কয়েক সেকেন্ডের মধ্যে trigger হয়।
  • AWS CodePipeline (polling) — CodePipeline নিজে check করে। দেরি হয়, অপ্রয়োজনীয় API call হয়। এটা ব্যবহার করবা না।

Pipeline Trigger করার পদ্ধতি

মোট ৩টা উপায়:

পদ্ধতিকীভাবেHistory-তে trigger দেখাবে
Automatic (source change) Source-এ নতুন version upload/push হলে CloudWatch event rule বা "Git push + commit ID"
Manual — Release change Pipeline page → Release change button StartPipelineExecution — তোমার IAM user দেখাবে
Pipeline creation Pipeline তৈরির সময় automatic CreatePipeline

Transitions disable/enable করা

Transition disable করলে source stage শেষ হওয়ার পর execution সেখানে আটকে থাকে। Deploy stage-এ যাওয়ার আগে তুমি ম্যানুয়ালি "Enable" করতে পারো — মানে controlled deployment।

  • Pipeline page-এ দুটো stage-এর মাঝে তীরচিহ্নে ক্লিক করো → Disable/Enable
  • Disable করার সময় reason লেখো (monitoring-এর জন্য কাজে লাগে)
  • Re-enable করলে শুধুমাত্র latest queued execution এগিয়ে যায়

Execution History ও Details দেখা

Pipeline list page

  • Latest execution status, source revision, কখন শুরু হয়েছে
  • Recent execution form (football team form-এর মতো — শেষ কয়েকটা success/fail)

Pipeline details page (pipeline name ক্লিক করো)

  • বড় box = Stage, ছোট box = Action
  • Blue = In Progress, Green = Succeeded, Red = Failed
  • প্রতিটি stage-এ execution ID দেখায় — source ও deploy-এর ID আলাদা হলে বুঝবে deployment হয়নি

Action details (View details ক্লিক করো)

  • Summary tab: last execution details, unique action execution ID
  • Input tab: Variable namespace, input artifacts, action-specific config। যেমন S3 source-এর জন্য PollForSourceChanges: false মানে CloudWatch Events ব্যবহার হচ্ছে।
  • Output tab: Output artifact-এর bucket, key, ETag, version ID

Execution details (execution ID ক্লিক করো)

  • Summary: trigger, start/end, duration
  • Timeline: প্রতিটি action-এর start/end/duration — action duration-এর sum মিলবে না কারণ transition time আলাদা
  • Variables: pipeline variables (যদি define করা থাকে)
  • Revisions: S3 version ID বা commit ID

Settings page (বাম menu-তে Settings)

  • Pipeline ARN, service role, version number (update করলে বাড়ে)
  • Artifact store bucket
  • Tags যোগ করো — best practice
Rerun button: Same input দিয়ে নতুন execution trigger করে। Debug করার সময় কাজে লাগে।

Pipeline Edit ও Parallel Action যোগ করা

Scenario: production bucket-এর পাশাপাশি অন্য region-এর আরেকটি bucket-এও একই সময়ে deploy করতে চাই।

Parallel action যোগ করার ধাপ

  1. Pipeline page → Edit
  2. Deploy stage → Edit stage
  3. বিদ্যমান action-এর পাশের box-এ Add action ক্লিক করো (same action group = parallel)
  4. Action name: DeployToUS
  5. Provider: Amazon S3 · Region: us-east-1
  6. Input artifact: SourceArtifact
  7. Bucket: second bucket · ✅ Extract file before deploy
  8. Done → Done → Save
flowchart LR SRC["Source Stage"] SRC -->|SourceArtifact| AG["Deploy Stage\n(Action Group)"] subgraph AG["Deploy Stage — একই Action Group = Parallel"] direction LR D1["Deploy (eu-west-1)\nOriginal action"] D2["DeployToUS (us-east-1)\nNew parallel action"] end

Deploy Stage-এ দুটো action একই action group-এ → parallel-এ চলে।

Sequential vs Parallel

  • Same action group → parallel
  • Add action group (নতুন group) → sequential (আগেরটি শেষ হলে শুরু হবে)
  • Add stage (নতুন stage) → sequential, আলাদা stage-এ
Pipeline update করলে automatic trigger হয় না। নতুন action execute করতে manually Release change করো।

Cross-region Deploy-এ IAM Permission

Second region-এ deploy action যোগ করলে pipeline-এর service role-এ নতুন permissions লাগবে। দুটো policy update করতে হয়:

Policy 1: Artifact store access

Default policy শুধু original region-এর artifact store allow করে। Second region-এর জন্য bucket ARN-এর region part wildcard করে দাও:

/* আগে (specific region) */
"Resource": "arn:aws:s3:::codepipeline-eu-west-1-ACCOUNT_ID"

/* পরে (all regions) */
"Resource": "arn:aws:s3:::codepipeline-*"

Policy 2: Deployment bucket access

Second deployment bucket-এর ARN যোগ করো:

"Resource": [
  "arn:aws:s3:::my-website-prod/*",
  "arn:aws:s3:::my-website-prod-us/*"   /* নতুন bucket */
]
Cross-region artifact store issue: কোনো region-এ প্রথমবার pipeline চালালে CodePipeline সেই region-এ artifact store bucket তৈরি করে। যদি error পাও, ওই region-এ একটি test pipeline তৈরি করে run করো — artifact store auto-create হবে। তারপর original pipeline-এ try করো।

Pipeline ও সম্পর্কিত Resources মুছে ফেলা

Pipeline delete করার দুটো উপায়

  • Pipeline list → select → Delete pipeline button
  • Pipeline details → Edit → Delete button

Confirmation dialog-এ text field-এ delete টাইপ করো।

Change detection resources

Default-এ "Delete change detection resources" চেক করা থাকে → CloudWatch Events rule-ও delete হয়। Uncheck করলে rule থেকে যাবে।

⚠️ যা automatically delete হয় না

Pipeline delete করলেও নিচেরগুলো থেকে যায় — manually সরাতে হবে:
  • Source S3 bucket
  • Deployment S3 bucket(s)
  • Artifact store S3 bucket (codepipeline-REGION-ACCOUNT) — অন্য pipeline ব্যবহার করে, রাখলেও চলে
  • IAM roles ও customer-managed policies

IAM cleanup

Pipeline delete করলে দুটো role থেকে যায়:

  • CodePipeline service role — pipeline execution-এ assume করা হত। একাধিক pipeline-এ reuse করা যায়, তাই রাখতে পারো।
  • CloudWatch Events trigger role — pipeline-specific। এটা delete করে ফেলো।

IAM Console → Policies → Filter: Customer managed → pipeline-related policies delete করো।

Artifact store cleanup (optional)

Artifact store bucket-এ প্রতিটি pipeline-এর জন্য একটি folder তৈরি হয়। Lifecycle rule যোগ করে পুরনো artifacts expire করতে পারো। Delete করলে শুধু সেই pipeline-এর folder delete করো।

Debug Tips

সমস্যাকোথায় চেক করবে
Pipeline trigger হচ্ছে না S3 bucket-এ versioning ON আছে? CloudWatch Events rule exist করে? Transition disabled?
Action "Access Denied" দিয়ে fail Pipeline settings → service role → attached policies চেক করো। Missing permission-এ inline policy যোগ করো।
Source ও Deploy stage-এ আলাদা execution ID Normal — যদি transition disabled ছিল। Re-enable করলে মিলে যাবে।
Cross-region deploy "networking error" Second region-এ artifact store নেই। ওই region-এ একটি temp pipeline বানাও।
Pipeline execution "Superseded" হয়ে গেছে Normal behavior। Staging-এ manual approval থাকলে বেশি দেখা যায়। Staging stage-এর lock আছে কিনা দেখো।
Deploy action "Didn't Run" Pipeline update-এর পর automatic trigger হয় না। Release change করো।

নিজেকে যাচাই করো

S3 bucket source হিসেবে ব্যবহার করতে দুটো requirement কী?
  1. Bucket অবশ্যই pipeline-এর same region-এ হতে হবে।
  2. Bucket-এ versioning enable থাকতে হবে — CodePipeline version ID দিয়ে revision track করে।
Pipeline update করার পর নতুন action execute করতে কী করতে হয়?

Pipeline update-এ automatic trigger হয় না। Pipeline page-এ Release change button ক্লিক করো → Confirm। এটা latest source version নিয়ে পুরো pipeline run করবে।

Superseded execution কখন ঘটে? Stage lock থাকলে কি ঘটতে পারে?

দুটো stage-এর মাঝে (transition-এ) অপেক্ষা করার সময় নতুন execution এসে গেলে পুরনোটি superseded হয়।

Stage lock থাকলে হয় না। Stage-এ enter করলে lock নেয় — নতুন execution ঢুকতে পারে না, তাই supersede-ও করতে পারে না।

Change detection-এ CloudWatch Events বনাম polling — কোনটি কেন ব্যবহার করবে?

CloudWatch Events ব্যবহার করো। কারণ:

  • Near real-time — upload হওয়ার সেকেন্ডের মধ্যে trigger হয়
  • Polling-এ CodePipeline নিয়মিত S3 check করে — unnecessary API calls, দেরি হয়
Pipeline delete করলে কী automatically মুছে যায় আর কী থেকে যায়?

মুছে যায় (default): CloudWatch Events/EventBridge trigger rule।

থেকে যায়: Source bucket, deployment bucket(s), artifact store bucket, IAM roles ও customer-managed policies। এগুলো manually delete করতে হবে।
